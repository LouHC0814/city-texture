# 发行流程

发行工作流在 GitHub Actions 上构建、实测、上传并核对离线版。程序运行本身不依赖 Actions 或 GitHub 账号。

## 准备一个版本

维护者同步更新以下内容并提交 PR：

1. `package.json` 中的程序版本和应用中的版本标注。
2. `.github/release.json` 中的发行版本。
3. `docs/发行说明-v版本号.md`、中文使用说明和 README 下载文件名。

目前发行流程接受 `数字.数字.数字` 格式，如 `0.4.0`。版本清单是发布信号：只有其变更合入 `main`，或维护者在 `main` 手动运行发行工作流时，才会进入发布阶段。PR 运行只验证和打包。

## 发布前做什么

- 校对版本清单与 `package.json`，确认对应发行说明存在。
- 执行 JavaScript、Python 检查与原始地图快照离线重建。
- 基于本次工作流的完整源码 SHA 打包 HTML、离线 ZIP、中文说明、版本信息及 SHA-256 清单。
- 用真实 Chrome 检查交互和最终发行 HTML 的断网运行。ZIP 内含样本包格式说明以及两份许可。
- 将这些已检查的文件保存为工作流 artifact；只有验证成功才启动具有 `contents: write` 权限的发布任务。

## 怎样核对上传内容

发布任务先创建草稿。若已有同版本草稿，必须关联完全相同的源码 SHA 才能继续；已公开版本或其他提交的草稿会使流程停止，避免覆盖或混合资产。

上传的外层文件名保持 ASCII，另附中文下载标签。随后将草稿中的所有附件重新下载，检查文件清单和每个字节，并核对版本信息中的源码 SHA、程序版本及 SHA-256 清单。全部通过后才公开发行版、更新 latest 下载入口。

工作流使用 GitHub 为本次运行提供的短期令牌，不需要添加个人访问令牌。只在发布任务授予写入权限；项目常规检查与 PR 验证保持只读。

## 失败后如何处理

验证失败时不会创建发行草稿。上传或回下载失败时草稿保持未公开，可检查日志并重跑同一提交；工作流会重新上传相同来源的文件。如果对应版本已经公开，重跑会停止，需为新的代码准备新的版本号。

普通使用者只需到 [最新发行页](https://github.com/LouHC0814/city-texture/releases/latest) 下载 HTML 或离线 ZIP。工作流记录和源码 SHA 供需要复核的人查看。
