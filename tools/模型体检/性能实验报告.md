> 采集时间：2026-10-19（第三次返修，**本轮重新采集**，不是复用旧数据）
> 环境：Windows x64 + Chrome 155.0.8059.80（`--headless=new`）+ Node v22.22.2
> GPU：`ANGLE (NVIDIA, NVIDIA GeForce RTX 5060 Laptop GPU, D3D11)`（真实 GPU，非 SwiftShader）

## 0 这份报告是什么 / 不是什么

**是什么**：在**这一个浏览器配置**下，对固定视口、固定模型、时间驱动的固定相机路线，连续采样 6 轮 × 10 秒（每轮剔除 1 秒预热），记录 rAF 间隔与渲染吞吐，并给出全部原始帧间隔（`rawDts`）。

**不是什么**（三条红线）：

1. **不是屏幕帧率**。测量时关闭了 vsync 与帧率上限（`--disable-frame-rate-limit --disable-gpu-vsync`），否则所有轮次都会被 BeginFrame 节拍卡死、毫无区分度。因此 fps 字段一律读作"该配置下的 rAF 吞吐"。
2. **不是 GPU 单帧耗时**。关掉 vsync 后测到的是调度间隔，不等于 GPU 执行时间。
3. **不能外推到真实手机或主项目性能预算**。手机档是 CDP 设备模拟 + CPU 4× 节流，不是真机。

### 0.1 本版删掉的三类结论（Codex 第三次验收 收尾1）

| 已删除 | 为什么必须删 |
| --- | --- |
| `canHit60` / `allCanHit60`（布尔判断） | rAF 间隔 ≤ 16.67ms 不等于"能满 60fps"，真实屏幕由 vsync 决定 |
| `headroom60x`（16.67 ÷ 帧时间）与"60Hz 余量 ×N" | 这是两个量的比值，不是 GPU 预算余量；分母不是 GPU 执行时间 |
| "全部可满 60fps"之类文字结论 | 上面两个字段的推论，字段没了结论也得没 |

`fps-summary.json` 里**不再存在**这些键（可用 `npm run vendor:verify` 之外的任何 JSON 工具搜 `canHit60|headroom60` 验证，结果应为空）。

### 0.2 FPS 分位数的定义（本版修正）

旧版 `fps.p95 = 1000 / p95(dt)`，这不是 FPS 分布的 P95，是"帧时间 P95 的倒数"。

现在按**逐帧瞬时帧率** `fps_i = 1000 / dt_i` 的分布取分位数。因为 `1000/x` 单调递减：

| 字段 | 定义 |
| --- | --- |
| `dtMs.p05 / p95 / p99` | 帧时间分布的下/上分位（**主指标**） |
| `fps.median` | `1000 / dtMs.median` |
| `fps.p95` | `1000 / dtMs.p05`（95% 的帧比它慢） |
| `fps.p05` | `1000 / dtMs.p95` |

另附 `fps.quantizationCaveat`：`performance.now()` 精度约 0.1ms，帧时间中位 0.6ms 时瞬时帧率的相对误差可达 ±15%，**fps 尾部只能当噪声量级参考**。

## 1 方法

| 项 | 设置 |
| --- | --- |
| 驱动 | 自写 CDP 客户端（Node 22 内置 `WebSocket`），零第三方依赖 |
| 视口 | 桌面 `Emulation.setDeviceMetricsOverride 1440×960 @dsf1`；手机 `390×844 @dsf3` |
| 手机档 | `setCPUThrottlingRate(4)` + `setTouchEmulationEnabled(true)` |
| 轮次 | 每档 3 轮，共 6 轮；每轮 10,000ms 采样 + 1,000ms 预热 |
| 相机 | **时间驱动**固定球面路线（固定角速度 rad/ms），同一时刻任何帧率下角度相同 |
| 计时 | 页面内 `requestAnimationFrame` 时间戳逐帧记录，测量期间不刷新 DOM |

### 1.1 为什么用 `headless=new`

本机 headful 窗口会被 Chrome 判定为遮挡：`document.visibilityState === "hidden"`、rAF **0 帧/2 秒**；加 `Page.bringToFront` + `Emulation.setFocusEmulationEnabled` 后首帧可见，但测量期间被后台节流到 **约 1 帧/秒**（帧间隔中位 3000ms），数据不可用。`headless=new` 下 rAF 正常推进，且 GPU 串仍是真实 RTX 5060。

### 1.2 实际画布 ≠ 视口

页面右侧有 340px 信息面板，所以 canvas 尺寸小于窗口。本报告记录**实测**值：

| 档位 | 视口 | CSS 尺寸 | canvas 像素 | drawingBuffer | renderer DPR |
| --- | --- | --- | --- | --- | --- |
| 桌面 | 1440×960 | 1075×834 | **1075×834** | **1075×834** | **1** |
| 手机模拟 | 390×844 | 390×748 | **585×1122** | **585×1122** | **1.5** |

- 桌面少掉的 365px 宽度 = 右侧面板 340px + 边框；834 高度 = 960 − 顶部工具条 126px。
- 手机：窄屏下侧栏隐藏，canvas 宽度回到 390 CSS px；页面把 `setPixelRatio` 上限设为 **1.5**，所以是 **585×1122**，**不是 390×844×3 = 1170×2532**。

> **截图尺寸 ≠ drawingBuffer 尺寸**：`measure/shots/mobile-*.png` 是 **1170×2532**（`Page.captureScreenshot` 按 dsf=3 光栅化整页），而 WebGL 实际绘制到 **585×1122**。前者是"截图像素"，后者是"渲染像素"。

### 2.3 两个档位的差异来自 CPU，不是像素

| 项 | 桌面 | 手机模拟 | 比值 |
| --- | --- | --- | --- |
| drawingBuffer 像素数 | 896,550 | 656,370 | **0.73×**（手机更少） |
| 帧时间中位 | 0.70 ms | 3.10 ms | **4.4×**（手机更慢） |
| CPU 微基准均值（200 万次 sin×cos） | 211.8 ms | 1,381.0 ms | **6.5×** |

- 手机档像素只有桌面的 **0.73 倍**，却慢了 **4.4 倍**；CPU 侧慢 **6.5 倍**（`setCPUThrottlingRate(4)` 只承诺 4×，实际放大更多，说明模拟本身也有开销）。
- → **在本实验条件下，瓶颈在主线程 CPU，不在像素填充率。** 这条只对本配置成立，不能直接搬到真机。

CPU 微基准三轮原始值：桌面 236.0 / 166.7 / 232.8 ms；手机 1579.1 / 845.5 / 1728.4 ms。手机档波动很大（±40%），单轮不可当精确值。

## 3 敏感性验证（证明这套管线是灵敏的，不是被固定节拍夹住）

把每帧 `renderer.render()` 调用次数放大到 ×1/×2/×4/×8/×16，各测 3 秒（桌面视口）：

| 每帧渲染次数 | 采样帧数 | 帧时中位 | 帧时 p95 | 帧时均值 |
| --- | --- | --- | --- | --- |
| ×1 | 4,930 | 0.6 ms | 0.9 ms | 0.61 ms |
| ×2 | 3,740 | 0.8 ms | 1.1 ms | 0.79 ms |
| ×4 | 3,689 | 0.8 ms | 1.2 ms | 0.80 ms |
| ×8 | 3,342 | 0.9 ms | 1.4 ms | 0.96 ms |
| ×16 | 1,461 | 1.2 ms | 5.3 ms | 2.05 ms |

- **均值 0.61 → 2.05 ms（×3.36）**，**p95 0.9 → 5.3 ms（×5.89）**，采样帧数 4,930 → 1,461（少 70%）。
- 三个信号方向一致 → 管线对负载敏感，×1 时的 0.70ms 不是某个固定节拍产生的常数。
- **为什么不用中位数判定**：负载放大后帧时间变成"多数帧仍快 + 少数帧很慢"的双峰，中位数对这种变化几乎不敏感（×16 时中位只从 0.7 涨到 1.2）。旧版正是用中位数判定，才会在 ×16 时得出"没上升"的结论——这是判定口径的问题，不是管线的问题。
- ×16 时最大单帧 487.9ms，说明存在偶发的长停顿（着色器/GC/驱动），本实验不追查其来源。

## 4 加载 → 首个可见帧

边界定义（写在页面里，可复核）：

- `t0`：`loadFromUrl` 开始（`fetch` 之前）
- `tRead`：`arrayBuffer()` 拿到
- `tParse`：`GLTFLoader.parseAsync` 返回（CPU 侧建图，**不含**首帧 GPU 上传）
- `tFirstRender`：`angleFit()` 后同步渲染一帧返回
- `tFirstVisible`：**连等两个 rAF** 之后 —— 第一个 rAF 是"这一帧被提交"，第二个是"它确实被呈现"

首屏实测（桌面，本地 127.0.0.1）：

| 阶段 | 计时区间 | 耗时 |
| --- | --- | --- |
| read | `t0 → arrayBuffer()` | 47.9 ms |
| **admission** | `tRead → ADM.check()` 返回 | **75.4 ms** |
| parse | `tAdmit → GLTFLoader.parseAsync` 返回 | 10.3 ms |
| firstRender | `tParse → angleFit()` 同步渲染完 | 1.0 ms |
| （rAF 等待 + DOM 更新） | 其余 | 352.5 ms |
| **load → 首个可见帧** | `t0 → 连等两个 rAF 之后` | **487.1 ms** |

- **准入单独计时**（本版新增字段 `admissionMs`）：75.4ms 里主要是"逐顶点做世界变换 + 算精确包围盒"——这份代码浏览器和 CLI 共用，代价就必须付在浏览器这边。
- GLTFLoader 本身只有 **10.3ms**。上一版把准入和解析合在一个 `parseMs` 里报 101.3ms，看不出是哪一段慢，本版拆开了。
- 352.5ms 的大头是**连等两个 rAF** 与 `countModelTriangles` 等同步 DOM/遍历工作；headless 下 rAF 的调度抖动较大，这个绝对值仅供参考，不是渲染耗时。

同名模型统计：模型几何 **147,604** 三角面；场景实际渲染 **147,988**（= 模型 + 地面 384）。两者分列，不混用。

## 7 结论与边界

**本次能证明**：

- 该模型在该浏览器配置下，桌面与手机模拟两档的帧时间中位分别为 **0.70ms / 3.10ms**，p95 为 **1.00ms / 7.10ms**
- 六轮共 **50,989 帧，>33ms 的帧为 0**
- 测量管线对负载敏感（均值 ×3.36、p95 ×5.89、帧数 −70%，三个信号一致）
- 两档差异来自主线程 CPU（像素更少反而更慢，CPU 基准慢 6.5×）
- 首屏里**准入**占 75.4ms、GLTFLoader 解析只占 10.3ms
- 页面零外网请求；阻断非本机请求后仍可加载渲染

**本次不能证明**（不要再从这些数据里推）：

1. 真实手机的帧率 —— 手机档是设备模拟 + CPU 节流，不是真机
2. GPU 单帧耗时 —— 关 vsync 后测到的是调度间隔
3. 主项目在真实 60Hz 屏幕上"够用"，或"有 N 倍余量" —— 真屏幕由 vsync 决定，且本实验测的不是 GPU 执行时间
4. 其他浏览器 / 其他 GPU 驱动的表现
5. 长时间运行的内存行为 —— 每轮只有 10 秒

## 8 复跑

```powershell
$node = (Get-Command node).Source
$root = (Resolve-Path ".").Path  # 在 tools/模型体检 目录执行
& $node "$root\measure\run-fps.cjs" --port 5173 --cdp 9333 --ms 10000 --warmup 1000 --rounds 3
```
